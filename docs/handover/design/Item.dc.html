How MCP auth actually works

By [AUTHOR NAME]
[cover image]

Most people meet auth in MCP the hard way. The server works on their laptop. Then someone asks who it is acting for, and nobody has a good answer.

The short version is simple. The client never hands the server a password. It gets a token from an authorisation server, scoped to what the user agreed to, and sends it with each call. The server checks the token, not the person.

The scope is the contract. If a tool can delete, the scope should say so, and the user should see it before they agree.

Refresh is where most servers go wrong. A long-lived token in a config file is a password with extra steps. Short tokens, refreshed quietly, with a clear way to revoke them.

Start with read-only tools. Add write scopes one at a time. Log the token id, never the token. And when a call fails, say which scope was missing, so the person can fix it without reading your code.

None of this is new. It is the same advice we gave web apps ten years ago. The difference is that now the thing holding the token can read, and it will do exactly what the scope allows.
